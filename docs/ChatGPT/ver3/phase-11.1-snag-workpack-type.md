# Phase 11.1 - Snag Workpack Type

## Status

DEFINE ONLY

This phase defines how snag workpacks exist within Jupiter.

This phase does not implement code, change schema, alter lifecycle behavior, or reopen Phase 10.12.

## Decision

`SNAG` is confirmed as a valid workpack type within Jupiter.

This type is part of workpack classification only.

It does not create a new lifecycle and does not alter the verified execution lifecycle core.

## Core Definition

SNAG workpacks are defined as defect-driven workpacks created to manage corrective maintenance activity for reported defects or snags.

SNAG workpacks are:

- independent of templates
- manually created

They are not generated from the template system and are not dependent on model-based planned maintenance content.

## Template Independence

SNAG workpacks must remain outside the template-generation chain.

That means:

- no maintenance template is required to create a SNAG workpack
- no standard task template is required to create a SNAG workpack
- no AD, SB, or SID template selection is required to create a SNAG workpack
- snag workpack creation is initiated directly by an operational defect need, not by scheduled maintenance planning

## Manual Creation Rule

SNAG workpacks are manually created by an authorized user when defect-driven work is required.

Manual creation means:

- the user intentionally creates the workpack
- the workpack is tied to a real aircraft defect or snag context
- the workpack is not auto-generated by template preview or template commit logic

This phase does not define the exact UI flow or fields for creation. It only locks the classification rule.

## Relationship to Normal Workpacks

The snag model must support both of the following realities:

- snags may exist inside normal workpacks
- snag workpacks may exist separately for defect-driven work

Interpretation:

- a normal scheduled workpack may contain snag items discovered or managed during its execution
- a dedicated SNAG workpack may also be opened independently when the defect itself is the primary reason for the work

This allows Jupiter to support both embedded snag handling and standalone defect-driven maintenance without changing the core workpack lifecycle.

## Lifecycle Constraint

This phase does not modify workpack lifecycle.

The locked workpack lifecycle remains:

`DRAFT -> ISSUED -> IN_PROGRESS -> CERTIFIED -> CLOSED`

The locked task lifecycle remains:

`OPEN -> IN_PROGRESS -> COMPLETED_BY_MECHANIC -> CERTIFIED_BY_ENGINEER -> LOCKED`

SNAG classification does not add, remove, rename, or bypass any lifecycle state.

## Explicit Non-Changes

This phase explicitly does not:

- introduce new workpack lifecycle states
- introduce a separate snag workpack lifecycle
- change execution rules
- change certification rules
- change close enforcement
- change CLOSED behavior
- modify Phase 10.12 verification or lock status

## Invariant

The invariant established by Phase 11.1 is:

`SNAG` is a valid workpack type, but not a lifecycle variant.

It changes why a workpack exists, not how the verified lifecycle core behaves.

## Boundary for Future Phases

Future snag phases may extend:

- snag creation workflow
- snag field definitions
- snag execution presentation
- recurring snag analysis
- snag closure rules within the already-locked lifecycle framework

Future snag phases may not:

- alter the core workpack lifecycle
- alter the core task lifecycle
- bypass certification
- bypass close enforcement
- modify CLOSED immutability

## Final Statement

Phase 11.1 defines SNAG as a valid, manual, template-independent workpack type that can coexist with normal workpacks and standalone defect-driven work, without changing any verified lifecycle, execution, certification, or close-control behavior.
